# Code-Audit Kimai Anfahrten, 14.11.2026, Stand 4abc1c4

## Urteil
Das Repo lässt sich warten. Die Rechenkerne liegen in eigenen Bausteinen und haben Tests: Steuer, Verpflegungspauschalen, Erkennung von Fahrten aus Dawarich, Import und Export. Die Schwäche liegt eine Ebene höher. Wer welche Fahrt sehen, ändern oder löschen darf und was in einem abgeschlossenen Monat erlaubt ist, steht nicht an einer Stelle. Dieselben Prüfungen sind in den Seiten (Controller: der Teil, der eine Anfrage aus dem Browser beantwortet) und in der Programmierschnittstelle (API) jeweils neu geschrieben. Ändert sich eine solche Regel, muss man alle Kopien finden. Für diese Kopien gibt es keine Unit-Tests, nur einzelne Fälle in den End-to-End-Tests. Das ist das erste Audit; einen Vergleich gibt es noch nicht. Eine `ARCHITECTURE.md` fehlt.

## Funde

### 1. Die Regel „abgeschlossener Monat nur mit Sonderrecht änderbar“ steht an neun Stellen
Ob ein Monat gesperrt ist und der Nutzer das Recht „gesperrte Monate bearbeiten“ hat, prüft jede Stelle neu. Das tun die Seiten für Fahrten, Vorschläge, Belege und Mietwagen sowie die API. Zwei Dienste bekommen das Ergebnis als Ja/Nein-Schalter von außen: das Anlegen von Arbeitswegen und der CSV-Import. Die eigentliche Sperre sitzt zusätzlich in der Datenbankschicht (der Teil, der jede Änderung vor dem Speichern sieht). Soll die Regel feiner werden, etwa Belege in gesperrten Monaten anders behandeln, muss man jede Kopie finden. Eine übersehene Kopie zeigt dem Nutzer einen falschen Knopf oder eine falsche Meldung. Vorschlag: Der Dienst für Monatssperren bekommt eine Funktion „darf dieser Nutzer das hier ändern“. Alle Stellen fragen nur noch sie, die Schalter-Parameter entfallen. Aufwand klein bis mittel. Risiko mittel: Die Sperre selbst hat keine Unit-Tests, nur der Import prüft sie mit. Beleg: `Controller/TripController.php:443`, `Controller/SuggestionController.php:322`, `Controller/SuggestionController.php:477`, `Controller/AttachmentController.php:93`, `Controller/RentalController.php:135`, `API/MileageApiController.php:288`, `API/MileageApiController.php:529`, `Service/CommuteGenerator.php:97`, `Service/TripCsvImporter.php:132`, `Doctrine/TripAuditListener.php:165`.

### 2. Wer bearbeiten, löschen oder das Team sehen darf, steht doppelt
Die Seiten teilen sich eine gemeinsame Prüfung für „darf bearbeiten“ und „darf löschen“. Die API schreibt dieselbe Prüfung ein zweites Mal selbst. Auch „darf die Teamseite sehen“ steht zweimal: einmal im Teamdienst, einmal wörtlich gleich im Aufbau des Menüs. Kommt ein neues Recht dazu oder ändert sich eine Bedingung, ändert man leicht nur eine Hälfte. Dann zeigt das Menü einen Eintrag, der zu „Zugriff verweigert“ führt, oder die API erlaubt etwas, das die Seite verbietet. Vorschlag: Die API nutzt die vorhandene Prüfung der Seiten, das Menü fragt den Teamdienst. Aufwand klein. Risiko mittel: Keine Unit-Tests; die End-to-End-Tests prüfen nur einige verbotene Zugriffe. Beleg: `API/MileageApiController.php:160`, `API/MileageApiController.php:520`, `Controller/TargetUserTrait.php:47`, `Controller/TargetUserTrait.php:56`, `EventSubscriber/MenuSubscriber.php:52`, `Service/TeamService.php:57`.

### 3. Die Vorgabewerte der Systemeinstellungen stehen zweimal
Elf Einstellungen haben ihren Vorgabewert an zwei Stellen: einmal im Formular der Systemeinstellungen, einmal dort, wo das Plugin den Wert liest. Darunter sind steuerlich wichtige Beträge: Kilometersatz für Auto und Motorrad, Höchstbetrag der Pendlerpauschale, Verpflegungspauschalen für 8 und 24 Stunden. Ändert der Gesetzgeber einen Satz und wird nur eine Stelle angepasst, sieht der Nutzer im Formular den neuen Wert und rechnet mit dem alten. Vorschlag: Die Vorgabewerte stehen einmal als Konstanten in der Konfiguration, das Formular übernimmt sie von dort. Aufwand klein. Risiko gering: Die Rechnungen mit diesen Werten sind getestet. Beleg: `EventSubscriber/SystemConfigurationSubscriber.php:46`, `EventSubscriber/SystemConfigurationSubscriber.php:123`, `EventSubscriber/SystemConfigurationSubscriber.php:131`, `Service/MileageConfiguration.php:68`, `Service/MileageConfiguration.php:83`, `Service/MileageConfiguration.php:93`, `Service/MileageConfiguration.php:124`, `Service/MileageConfiguration.php:133`.

### 4. Ein neuer Arbeitsweg wird an drei Stellen zusammengesetzt
„Start ist die Wohnung, Ziel die Arbeit, Strecke die hinterlegte Entfernung“ steht in drei Fassungen: im Formular für eine neue Fahrt, in der API und im Dienst, der mehrere Arbeitswege auf einmal anlegt. Für alle neuen Fahrten gibt es schon einen gemeinsamen Dienst, der Vorgaben setzt. Die Vorgaben für Arbeitswege stehen aber nicht dort. Soll ein Arbeitsweg künftig etwas mehr mitbekommen, etwa das Fahrzeug für den Arbeitsweg, muss man drei Stellen ändern. Vorschlag: Der vorhandene Fahrtendienst bekommt eine Funktion „neuer Arbeitsweg“, die drei Stellen rufen sie. Aufwand klein. Risiko mittel: Das Anlegen von Arbeitswegen hat keine Unit-Tests, nur einen Seitenaufruf im End-to-End-Test. Beleg: `Controller/TripController.php:505`, `API/MileageApiController.php:135`, `Service/CommuteGenerator.php:103`, `Service/TripService.php:31`.

### 5. Eine Fahrt samt Belegen löschen steht zweimal, für Mietwagen ein drittes Mal
Beim Löschen einer Fahrt muss das Programm erst die Beleg-Dateien von der Platte entfernen und dann den Datensatz. Die Datenbank entfernt nur die Einträge der Belege, nicht die Dateien. Seite und API schreiben diese Reihenfolge je selbst, für Mietwagen steht sie ein drittes Mal. Ändert sich, was beim Löschen mitgehen muss, bleiben bei einer vergessenen Kopie Dateien als Waisen auf dem Server liegen. Vorschlag: Je eine Funktion „Fahrt löschen“ und „Mietwagen löschen“ im Dienst, die die Dateien mitnimmt. Aufwand klein. Risiko mittel: Das Löschen einer Fahrt ist nirgends getestet. Beleg: `Controller/TripController.php:224`, `API/MileageApiController.php:165`, `Controller/RentalController.php:161`.

### 6. CSV-Dateien werden an drei Stellen von Hand geschrieben, zwei davon ohne Test
Drei Exporte bauen ihre CSV-Datei (Tabelle als Text zum Öffnen in Excel) jeweils selbst. Jeder setzt das Kennzeichen für Umlaute, Trennzeichen und Zahlenformat und schützt die Zellen gegen eingeschleuste Formeln. Das sind die Fahrtenliste, die Kundenübersicht und das Fahrtenbuch für das Finanzamt. Nur die Fahrtenliste liegt in einem eigenen, getesteten Baustein. Die beiden anderen stehen direkt in den Seiten. Soll sich am Format etwas ändern, etwa Komma oder Punkt, muss man drei Stellen gleich ändern. Das Fahrtenbuch, die steuerlich wichtigste Datei, prüft dann kein Unit-Test. Vorschlag: Ein kleiner gemeinsamer CSV-Schreiber. Die Spalten von Fahrtenbuch und Kundenübersicht wandern als eigene Exporte neben den vorhandenen und bekommen Tests wie dieser. Aufwand klein bis mittel. Risiko: Die Tests kommen zuerst, für das Fahrtenbuch gibt es bisher nur einen Abruf im End-to-End-Test. Beleg: `Service/TripCsvExporter.php:20`, `Controller/OverviewController.php:123`, `Controller/LogbookController.php:246`.

### 7. Derselbe Ausdruck für den Nutzer in der Adresse steht 27 Mal
Schaut man die Fahrten eines anderen Nutzers an, trägt jede Seite dessen Nummer in die Adresse ein; bei den eigenen Fahrten bleibt das Feld leer. Diese Zeile steht 27 Mal in elf Seiten, dazu fünf fast gleiche kleine Hilfsfunktionen. Soll das Feld anders heißen oder anders befüllt werden, sind das 27 Änderungen. Vorschlag: Eine Funktion dafür in der gemeinsamen Nutzerprüfung der Seiten. Aufwand klein. Risiko gering: Die Änderung ist mechanisch, die End-to-End-Tests rufen die Seiten mit fremdem Nutzer auf. Beleg: `Controller/TripController.php:81`, `Controller/LogbookController.php:66`, `Controller/PlaceController.php:195`, `Controller/VehicleController.php:150`, `Controller/SuggestionController.php:472`, `Controller/TargetUserTrait.php:12`.

### 8. Es gibt keine `ARCHITECTURE.md`, und der Ordner der Dienste mischt vier Arten von Bausteinen
Nirgends steht, wie das Repo gebaut sein soll und wohin Neues gehört. Der Ordner `Service` hält 42 Dateien ohne Unterordner. Darin liegen die Anbindung an fremde Server (Dawarich, Adresssuche), die Steuerrechnung, die Erkennung von Fahrten, Hilfen nur für die Seitenköpfe und die Antwort der API auf „welche Version läuft“. Wer etwas Neues anlegt, legt es dorthin, weil alles dort liegt. Die Funde 1 bis 6 sind auch so entstanden: Ohne festgelegten Ort für Regeln schreibt jede Seite ihre eigene Kopie. Vorschlag: Die Hauptsitzung legt `ARCHITECTURE.md` an (Skill `architektur`). Darin steht, dass Rechte- und Sperrregeln in Dienste gehören und nicht in Seiten und API, und die Dienste werden nach Art gruppiert. Aufwand mittel. Risiko gering, solange nur verschoben wird. Beleg: `Service/MileagePages.php:16`, `Service/ApiInfo.php:12`, `Service/DawarichClient.php:13`, `Service/TaxCalculator.php:36`.

### 9. Der nachgebaute Dawarich-Server steht zweimal
Für Demo und End-to-End-Tests gibt es je einen kleinen Ersatz-Server, der die Antworten von Dawarich nachahmt. Die Demo-Fassung nennt sich selbst eine Kopie der Test-Fassung. Beide haben rund 230 Zeilen, davon 82 gleich, und dieselben fünf Adressen. Nur die Orte unterscheiden sich: Hamburg für die Demo, Berlin für die Tests. Ändert Dawarich seine Schnittstelle und das Plugin folgt, müssen beide Ersatz-Server mitgezogen werden. Sonst zeigt die Demo Fehler, die die Tests nicht sehen. Vorschlag: Ein Ersatz-Server, der seine Orte aus einer Datei liest; die Demo gibt ihre Welt-Datei, die Tests eine eigene. Aufwand mittel. Risiko gering: Die End-to-End-Tests zeigen sofort, ob der Server noch stimmt. Beleg: `demo/fake-dawarich/index.php:4`, `demo/fake-dawarich/index.php:31`, `tests/e2e/fake-dawarich/index.php:25`.

### 10. Bestandsliste: drei Einträge trennen sich an einer klaren Naht, der Rest ist in Ordnung
Die Bestandsliste ist die Liste der Stellen, die heute über den Grenzen für Länge und Verzweigung liegen. Drei Einträge haben eine klare Trennstelle.

- Die Rechnung der Verpflegungspauschalen hat 144 Zeilen und drei Schritte: Dienstfahrten zu Reisen verbinden, Reisen auf Tage verteilen, Tage mit der Drei-Monats-Regel bewerten. Jeder Schritt kann eine eigene Funktion werden; Tests sind vorhanden.
- Das Formular einer Fahrt hat zwei Wege, die nichts teilen: Strecke aus Dawarich messen und speichern.
- Die Prüfung vor dem Speichern in der Datenbankschicht behandelt neue, geänderte und gelöschte Fahrten in drei getrennten Schleifen.

So bleiben dürfen: das Übernehmen der API-Felder auf eine Fahrt (eine flache Liste gleichartiger Felder), der Aufbau des Fahrtformulars und der Systemeinstellungen (lange Listen), die Datenbank-Migration (läuft einmal) und der Ablauf der End-to-End-Tests (ein Drehbuch).

Aufwand je Eintrag klein.
